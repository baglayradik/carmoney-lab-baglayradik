# Spec MILEAGE: пробег больше 400 000 км -> review

ID задачи: `MILEAGE`. Дата: 2026-09-30. Основа: `docs/intent/intent_MILEAGE.md`
(далее — intent; ссылки вида «intent §3 п. 1» — на его разделы) и ответы заказчика
из `docs/intent/grill_MILEAGE.md` (далее — grill, вопросы 1–4).

Спека описывает поведение, а не реализацию: файлы, ключ конфига и порядок шагов —
в `docs/plan/plan_MILEAGE.md`.

Термины:

- Решение — `approve` | `review` | `reject` (код:
  `backend/src/Domain/DecisionEngine.php:16-18`).
- LTV — запрошенная сумма / оценочная стоимость × 100, округление до двух знаков
  (код: `backend/src/Domain/LtvCalculator.php:25`; в тестах 450 000 / 900 000 = 50.0,
  `tests/Unit/AssessmentServiceTest.php:47-49`).
- Лимит — `approved_limit` в ответе (код: `backend/src/Domain/AssessmentService.php:39`).
- Валидная заявка — заявка, проходящая `ApplicationValidator`: все поля в диапазонах
  `backend/config/rules.php`.

## 1. Входит / не входит

Входит (объём поведения):

1. Правило пробега в расчёте решения: пробег больше 400 000 км понижает `approve`
   до `review` (REQ-MILEAGE-01).
2. Границы правила: 400 000 км включительно — допустимый пробег, `review` —
   с 400 001 (REQ-MILEAGE-01, REQ-MILEAGE-02).
3. Сочетание с решением по LTV: `review` не переопределяется, `reject`
   сохраняется (REQ-MILEAGE-03, REQ-MILEAGE-04).
4. Поведение при отсутствующем или null пробеге: остаётся ошибка валидации
   (в API — HTTP 422), решение не рассчитывается (REQ-MILEAGE-05).
5. Сохранение существующего поведения: пороги LTV (REQ-MILEAGE-06), диапазон
   валидации пробега 0–500 000 км (REQ-MILEAGE-07), лимит (REQ-MILEAGE-08).

Не входит (intent §5; подтверждено grill, вопрос 4):

1. Изменение валидации пробега: диапазон 0–500 000 км, тексты ошибок и кейс
   «пустая строка → 0» остаются как есть. Текущее поведение кейса: пустая строка
   в `mileage` нормализуется в 0 (`(int) '' === 0`, код:
   `backend/src/Domain/ApplicationValidator.php:43`) и проходит валидацию;
   решение при этом считается по LTV, так как 0 не больше 400 000 (производное от
   REQ-MILEAGE-02).
2. Пересчёт уже сохранённых решений — правило применяется только при расчёте
   решения по новой заявке.
3. Фронтенд, схема и данные БД, код сохранения заявок, форма API-ответа.
4. Расчёт лимита по возрасту авто — отдельная задача LOAN-12.
5. HTTP-проверка приложения целиком (Feature-уровень, `tests/Feature`) —
   отдельное ДЗ.

## 2. Требования

Требований сверх intent здесь нет: REQ-01–05 выводятся из intent §1 «Замысел» и
§3 п. 1–3, REQ-06–08 — из §3 п. 4–6.

### REQ-MILEAGE-01

Пробег больше 400 000 км понижает решение `approve` до `review`.

Источник: intent §1 «Замысел», §3 п. 1–2; grill, вопрос 3 («правило только
понижает approve до review»). Число 400 000 — постановка задачи (intent §1);
граница — grill, вопрос 1.

### REQ-MILEAGE-02

При пробеге 400 000 км и меньше правило пробега не срабатывает: решение
определяется только по LTV.

Источник: intent §3 п. 1; grill, вопрос 1 («400 000 включительно — допустимый
пробег, решение по LTV; review с 400 001»).

### REQ-MILEAGE-03

Решение `review` при пробеге больше 400 000 км остаётся `review`.

Источник: intent §1 «Замысел», §3 п. 2; grill, вопрос 3.

### REQ-MILEAGE-04

Решение `reject` по LTV (LTV больше 85.0) при пробеге больше 400 000 км остаётся
`reject`.

Источник: intent §3 п. 2; grill, вопрос 3 («reject по LTV сохраняется»). Число
85.0 — `backend/config/rules.php:45` (`review_max`).

### REQ-MILEAGE-05

Заявка без пробега (ключ `mileage` отсутствует или равен `null`) — ошибка
валидации по полю `mileage` (в API — HTTP 422), решение не рассчитывается.

Источник: intent §3 п. 3; grill, вопрос 2. Код:
`backend/src/Domain/ApplicationValidator.php:43-46` (`?? -1` относит null
к отсутствию), HTTP 422 — `backend/src/Http/ApplicationController.php:30, 61`.

### REQ-MILEAGE-06

Пороги решения по LTV не меняются: `approve` при LTV меньше 60.0; `review` при LTV
от 60.0 до 85.0 включительно; `reject` при LTV больше 85.0.

Источник: intent §3 п. 4. Числа 60.0 и 85.0 — `backend/config/rules.php:44-45`;
семантика границ — `backend/src/Domain/DecisionEngine.php:30-41` (approve — строго
меньше 60.0, review — до 85.0 включительно).

### REQ-MILEAGE-07

Диапазон валидации пробега не меняется: от 0 до 500 000 км включительно; пробег
больше 500 000 км — ошибка валидации по полю `mileage` (в API — HTTP 422) и до
расчёта решения не доходит.

Источник: intent §3 п. 5; grill, вопрос 4. Числа 0 и 500 000 —
`backend/config/rules.php:23` (`max_mileage_km`), проверка —
`backend/src/Domain/ApplicationValidator.php:44-45`. Следствие для REQ-MILEAGE-01:
правило действует только в полосе 400 001–500 000 (intent §3 п. 5).

### REQ-MILEAGE-08

Лимит не меняется: при решении `approve` — равен запрошенной сумме заявки, при
решениях `review` и `reject` — 0.

Источник: intent §3 п. 6 (`review` — 0, `approve` — запрошенная сумма); при
`reject` — 0: код `backend/src/Domain/AssessmentService.php:39` и тест
`tests/Unit/AssessmentServiceTest.php:64-71`; границы плана подтверждены grill,
вопрос 4.

## 3. Критерии приёмки

Формат Given / When / Then; в квадратных скобках — покрываемые требования.
AC проверяются на уровне домена (юнит-тесты); сквозная HTTP-проверка — вне задачи
(§1 «Не входит», п. 5). HTTP 422 в формулировках — существующее поведение
контроллера: `backend/src/Http/ApplicationController.php:30, 61`.

Числа в AC и их источники:

- Пробег: 400 000 и 400 001 — grill, вопрос 1; 399 999 и 500 001 — производные
  границы (400 000 − 1, 500 000 + 1); тройка 399 999 / 400 000 / 400 001 закреплена
  конвенцией спеки (`docs/spec/README.md`); 500 000 —
  `backend/config/rules.php:23`; 0 — нижняя граница того же диапазона
  (`backend/src/Domain/ApplicationValidator.php:44`); 96 000 — существующая
  фикстура ниже порога (`tests/Unit/AssessmentServiceTest.php:38`).
- LTV: пороги зон 60.0 и 85.0 — `backend/config/rules.php:44-45`; 50.0 —
  approve-зона, используется в плане §3 и тесте
  `tests/Unit/AssessmentServiceTest.php:47-49`; 59.9 — сразу под порогом
  (60.0 − 0.1); 72.3 — review-зона, `tests/Unit/DecisionEngineTest.php:32`
  и план §3; 95.0 — reject-зона, `tests/Unit/AssessmentServiceTest.php:68`
  и план §3; 85.01 — сразу за порогом review,
  `tests/Unit/DecisionEngineTest.php:34`.
- Лимит 0 — intent §3 п. 6, `backend/src/Domain/AssessmentService.php:39`.

## 4. Open questions из intent — статус

1. Граница «не больше 400 000 км»: ровно 400 000 — допустимый пробег или уже
   review? — Закрыт: ответ заказчика, grill вопрос 1 — 400 000 включительно,
   review с 400 001. Отражено в REQ-MILEAGE-01, REQ-MILEAGE-02 и AC-01–03.
2. Отсутствующий/null пробег: 422 или «неизвестный пробег» уходит в расчёт? —
   Закрыт: ответ заказчика, grill вопрос 2 — 422, валидатор не меняется.
   Отражено в REQ-MILEAGE-05 и AC-06–07.
3. Пробег за порогом при reject-уровне LTV: reject или review? — Закрыт: ответ
   заказчика, grill вопрос 3 — reject сохраняется. Отражено в REQ-MILEAGE-04
   и AC-05.
4. Границы задачи. — Закрыт: ответ заказчика, grill вопрос 4 — как в плане;
   «пустая строка → 0» в задачу не входит. Отражено в §1 «Входит / не входит».
5. Бизнес-обоснование правила и порога 400 000. — Перенесён: остаётся открытым,
   адресат — заказчик (intent §4, вопрос 5). На требования MILEAGE не влияет:
   каждый REQ опирается на ответы заказчика (grill, вопросы 1–4) и код,
   бизнес-обоснование в формулировки REQ и AC не входит.
