# План MILEAGE: пробег больше 400 000 км -> решение review

ID задачи: `MILEAGE`. Дата: 2026-09-30.

Правило из постановки: «пробег авто не больше 400 000 км, иначе решение review».

Трактовка по умолчанию (открытый вопрос 1 в конце): пробег больше 400 000 км
понижает `approve` до `review`, но не перекрывает `reject` по LTV — остаётся
более строгое решение. Граница «не больше»: ровно 400 000 — допустимый пробег,
`review` начинается с 400 001 (открытый вопрос 4 — подтверждение).

Источники: текст задачи; `docs/setup/code_map.md` (раздел «Правило "пробег > 400 000
км -> review"»); код, сверенный по состоянию на 2026-09-30. Все места, где читается
пробег, найдены поиском по `mileage|max_mileage` и совпали с картой кода;
субагент scout не потребовался — карта кода уже содержит полный разбор, места
сверены с кодом построчно.

Ключевой факт из карты кода: сейчас пробег участвует только в валидации
(`ApplicationValidator`, диапазон 0..500 000) и в сохранении в БД; на решение
approve/review/reject он не влияет. `DecisionEngine::decide()` принимает только
`float $ltv`.

## 2. Шаги

1. `rules.php`: добавить `vehicle.review_mileage_km => 400000`. Поведение пока не меняется — порог никем не читается.
2. `DecisionEngine`: конструктор `__construct(array{approve_max:float,review_max:float} $thresholds, int $reviewMileageKm)`; в `decide(float $ltv, int $mileage): string` порядок проверки — сначала reject по LTV (LTV > `review_max`), затем review (LTV >= `approve_max` ИЛИ пробег > `review_mileage_km`), иначе approve. Точная семантика LTV-границ сохраняется: approve при LTV < `approve_max`, reject при LTV > `review_max` (сравнение `400 000` — строгое: `>`).
3. `AppFactory`: передать порог в конструктор `DecisionEngine` (строка 37).
4. `AssessmentService`: передать `$input['mileage']` в `decide()` (строка 33).
5. Тесты — по разделу 3.
6. Проверка: `make test`, затем `make lint`. Шаги 2–5 делаются одним коммитом: между сменой сигнатуры `decide()` и обновлением тестов набор красный (ArgumentCountError), это ожидаемо, не откатывать.

## 3. Тесты

Существующие фикстуры (`mileage` 84 000 и 96 000) ниже порога — ожидания старых
тестов не меняются, кроме мест, где вызывается `decide()` (нужен второй
аргумент, безопасное значение — например 100 000).

`tests/Unit/DecisionEngineTest.php` (LTV зелёной зоны — 50.0, если не сказано иное):

- `testKeepsApproveWhenMileageBelowReviewThreshold` — пробег ниже порога, решение по-прежнему approve.
- `testKeepsApproveAtExactMileageThreshold` — пробег ровно на пороге, решение approve.
- `testSendsToReviewWhenMileageAboveThreshold` — пробег сразу за порогом, решение review.
- `testKeepsRejectWhenMileageAboveThresholdAndLtvAboveReviewMax` — пробег за порогом + LTV 95.0 -> reject (трактовка по умолчанию, вопрос 1).
- `testKeepsReviewWhenMileageAboveThresholdAndLtvInReviewZone` — пробег за порогом + LTV 72.3 -> review.
- Существующий провайдер `ltvValues` — каждой строке добавить второй аргумент (безопасный пробег), ожидания решений не меняются: регрессия LTV-семантики.

Граничные значения (отдельными строками):

- 399 999 -> approve (решение по LTV)
- 400 000 -> approve (граница «не больше», включительно)
- 400 001 -> review
- пустой пробег (ключ `mileage` отсутствует или null) -> ValidationException с ошибкой `mileage`, HTTP 422, решение не считается (существующее поведение, не меняется)

`tests/Unit/AssessmentServiceTest.php` (хелпер `payload()` получает параметр пробега):

- `testSendsToReviewWithZeroLimitWhenMileageAboveThreshold` — пробег 400 001, LTV 50.0 -> decision review, approved_limit 0 (раньше был approve).
- `testKeepsApproveAtExactMileageThreshold` — пробег 400 000, LTV 50.0 -> approve, approved_limit = запрошенной сумме.
- `testKeepsRejectWhenMileageAboveThresholdAndLtvHigh` — пробег 400 001, LTV 95.0 -> reject, approved_limit 0.
- `testThrowsWhenMileageIsMissing` — payload без ключа `mileage` -> ValidationException.

`tests/Unit/ApplicationValidatorTest.php`:

- `testRejectsMissingMileage` — в payload нет ключа `mileage` -> ValidationException, в `errors()` есть ключ `mileage` с текстом «Пробег от 0 до 500000 км».
- `testRejectsNullMileage` — `mileage => null` -> то же самое (`?? -1` относит null к отсутствию).

Существующее поведение, зафиксированное без нового теста: пустая строка `''`
в `mileage` сейчас нормализуется в 0 и проходит валидацию (`(int) '' === 0`);
фронт при пустом поле тоже отправит 0 (`Number('') === 0`, но поле `required`
со значением по умолчанию). Тест на это не добавляем — вопрос 3.

Ручная проверка (по желанию, после `make up`):
`curl -X POST http://localhost:8080/api/ltv -d '{"vin":"XTA21099998765432","year":2019,"mileage":400001,"market_value":900000,"requested_amount":450000,"term_months":24}' -H 'Content-Type: application/json'` -> `decision: "review"`.

## 4. Риски

1. Существующая проверка `max_mileage_km` (500 000, `rules.php:23`, `ApplicationValidator:44–46`): новое правило работает только в полосе 400 001–500 000; пробег больше 500 000 в решение не доходит — это по-прежнему 422 валидации. Нельзя «выровнять» `max_mileage_km` до 400 000: изменится диапазон валидации и текст ошибки, это другая задача. Если порог `review_mileage_km` когда-нибудь поднимут выше 500 000, правило не сработает — валидация отсечёт раньше.
2. Смена сигнатуры `decide()`: мест вызова три — `AssessmentService:33`, `DecisionEngineTest:23`, конструктор в `AssessmentServiceTest:27`. Все обновляются одним коммитом, иначе ArgumentCountError. Красный `make test` между шагами 2 и 5 — ожидаемый, не признак бага.
3. Приоритет review/reject: план берёт «остаётся более строгое решение» (reject не перекрывается). Если заказчик ответит на вопрос 1 «буквально: всегда review», поменяются порядок веток в `decide()` и тесты `testKeepsReject...` — правка после ответа, не во время реализации.
4. Заметное изменение поведения: заявки с пробегом 400 001–500 000 и низким LTV, которые раньше получали `approve` с лимитом = сумме, теперь уходят в `review` с `approved_limit = 0` (автоматически через `AssessmentService:39`). Форма API-ответа не меняется — только значения; фронт и логи (`ApplicationController:36–42`) изменений кода не требуют.
5. Прокидка конфига: `DecisionEngine` теперь читает пороги из двух секций (`ltv` и `vehicle`). Забытая правка `AppFactory:37` даст ArgumentCountError — и юнит-тесты её не ловят: `AssessmentServiceTest:24–29` собирает граф сервиса сам (`:27` — `new DecisionEngine($rules['ltv'], порог)` после шага 5), минуя `AppFactory`; `tests/Feature` пуст, ни один тест не поднимает приложение, поэтому `make test` и `make lint` с такой дырой остаются зелёными (`make lint` — только `php -l`, нехватка аргумента — ошибка времени выполнения). Ошибка проявляется лишь на первом HTTP-запросе: `public/index.php:9` вызывает `AppFactory::create()`, сервис собирается до регистрации роутов (`AppFactory:30–39`), так что упадёт любой запрос, включая `GET /health` (500). Ловится ручной проверкой после `make up`: `curl http://localhost:8080/health`. Надёжное закрытие дыры — Feature-тест, собирающий приложение через `AppFactory`, но это ДЗ.1 и в план не входит (см. «не входит»).
6. `rules.php` правится только решением человека (`docs/agent-rules.md`): в этой задаче человек прямо велел добавить порог — добавляем новый ключ; существующие значения (`max_mileage_km`, `ltv.*`, `amount.*`, `term.*`) не менять.
7. Данные: фикстуры тестов (84 000, 96 000) и максимум в `db/seed.sql` (296 000) ниже порога — регрессий в тестах и расхождений seed-заявок с новым правилом нет; `schema.sql`, `seed.sql`, репозиторий и фронтенд не трогаем.

Не входит (в реализации не делать):

- расчёт лимита по `ltv_by_age` (задача LOAN-12);
- изменение валидации пробега: диапазон, тексты ошибок, кейс пустой строки `''` -> 0;
- пересчёт уже сохранённых решений — правило применяется только к новым заявкам;
- фронтенд, схема и seed БД, репозиторий, форма API-ответа;
- HTTP Feature-тест (каталог `tests/Feature` пуст и заполняется в ДЗ.1) — при желании туда кладётся POST `/api/ltv` с пробегом 400 001 -> review.

## Вопросы, на которые без заказчика не ответить

1. Пробег больше 400 000 при reject-уровне LTV (LTV > 85): оставить `reject` (дефолт плана — остаётся более строгое решение) или переводить в `review` (буквальное прочтение «иначе решение review»)? От ответа зависит порядок веток в `decide()` и два теста.
2. Пустой/отсутствующий пробег: сейчас это 422 «Пробег от 0 до 500000 км», решение не считается. Устроит ли, что новое правило на этот случай не влияет, или «неизвестный пробег» должен давать `review`?
3. Пустая строка `''` в `mileage` сейчас превращается в 0 и проходит валидацию (и фронт при пустом поле отправит 0). Считать ли это ошибкой валидации? Если да — это отдельная задача, в план MILEAGE не входит.
4. Подтверждение границы: ровно 400 000 — допустимый пробег (решение по LTV), `review` — с 400 001. Правильно ли понята граница «не больше 400 000 км»?
